# 工作台自定义清洗标签 v0.2.12

状态：implemented_unverified。代码与本地模拟测试已完成；真实 TT、手机和模型请求待用户现场验证。

## 范围与实现

- 基于 `main@9a6f9209ee8dc115e981565bd6d77d32244d12ed`，开工工作树干净。
- 入口文件已读：`AGENTS.md`、工作台 model/controller/context/view、相关 runtime/UI 测试及 `docs/workbench.md`；另核对记忆项目 `work/daily-memory-mvp-baibai@348a8dfc1b7f3030ca2517f41720050765e63e94` 的自定义清洗标签。
- 记忆项目原有实现只有标签名匹配，属性规整、同名嵌套和未闭合块不能满足本次需求，因此只参考输入框、添加和可删除标签的交互。
- 全局设置增加 `cleanTags: string[]`，schema 3 → 4，旧配置补空列表。支持名称和属性条件、多规则、规范化去重、逐项移除，以及独立规则 JSON 导入／导出。取消设置不持久化；保存和导出等待正在读取的规则文件，关闭后的异步结果不写入新窗口。
- 新 `tag-filter.js` 以状态机顺序扫描，按名称查找规则，用同名深度处理嵌套。不开 DOM、不拼用户正则，不对每条规则反复扫描全文；匹配开标签未闭合时清洗到当前消息末尾。
- 每次捕获已选正文时过滤一次。原始 `rawMessages` 保留给来源签名；`promptMessages` 供冻结提示词、三项正文宏、逐楼预算校验和实际请求预览。整楼变空仍保留楼号和包装。
- 正文主 API 和独立 API 共用上述捕获路径；设定、世界书、历史总结及工作台会话保持原有语义。没有修改记忆插件或 TT。

首次全量 239/239 通过后，最终静态复核发现“无效标签文件导入期间点击保存，错误可能被吞掉”的实际异步问题。修正用于等待的 Promise 与显示错误的处理后，先跑 UI 反例，再对最终候选重跑一次全量；没有因纯文档变更重跑测试。

性能专门检查了 36 万字符的长属性、5 万层未闭合标签、2,000 条短消息，均确认排队计时器在清洗完成前执行。每 32,768 个扫描字符让出一次任务，短消息也累计预算。另一次约 209.7 万字符的合成混合正文测得约 131 ms 总耗时，期间计时器执行 61 次，最大观测间隔约 7.36 ms；仅为本地 Node 指标，不外推手机帧率。

保存标签、页面渲染及流式 token 不引入正文读取、后台轮询或重新清洗。集成反例确认一次预览只读取所选正文范围一次；被清洗部分的原文变更仍被来源签名拒绝。

## 改动量、限制与回退

实现／版本／样式约新增 220 行、移除 16 行；测试新增 206 行。实现处于开工预估的 200–300 行内，测试超过预估的 100–150 行，额外覆盖了空楼、宏、原文签名和异步规则导入。

未完成现场项：用户安装版 TT 的实际提示词／模型请求、Android WebView 的视觉布局及运行响应性。Node、LinkeDOM 和宿主模拟通过不等于原生现场 verified。没有在测试中调用宿主正文写入。

数据影响仅为新增全局清洗配置和任务配置中的本次规则记录，不迁移或改写聊天、已存设定、归档记录、草案或旧快照。过滤只影响之后捕获的正文，不能追溯删除既有工作台对话或模型已收到的内容。

无需过滤时删除全部标签并保存即可恢复原发送行为；规则可先独立导出备份。代码回退可 revert 此次功能提交，不需要删除数据库。无新增服务、依赖或下游施工项。
